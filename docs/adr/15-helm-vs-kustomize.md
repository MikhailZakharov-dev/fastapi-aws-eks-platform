# ADR: шаблонизация манифестов — Helm, не Kustomize

- **Статус:** принято
- **Контекст:** сервис раскатывается в две среды (dev/prod) одного кластера.
  Манифесты различаются двумя полями — число реплик и тег образа; позже
  добавятся resources и host. Сырые манифесты пришлось бы держать копией на
  каждую среду. Варианты: (A) Helm — шаблоны с параметрами в values;
  (B) Kustomize — базовые манифесты плюс патчи-оверлеи.
- **Решение:** Helm.
- **Почему:** платформенные компоненты стека (kube-prometheus-stack, Loki,
  External Secrets Operator, AWS Load Balancer Controller) распространяются
  Helm-чартами, то есть Helm в кластере нужен в любом случае. Вести собственное
  приложение Kustomize'ом означало бы держать два инструмента и две модели
  рендера ради экономии, которой нет.
- **Цена решения:** шаблон перестаёт быть валидным YAML — чтобы увидеть, что
  уедет в кластер, нужен рендер (`helm template`). База Kustomize читалась бы
  как обычный манифест. Принимаем осознанно.
- **Границы применения:** релизы Helm не используются. ArgoCD рендерит чарт сам
  и применяет результат, поэтому `helm list` в кластере пуст, а истина о
  желаемом состоянии живёт в gitops-репозитории, не в кластере.
- **Дисциплина параметризации:** в values уезжает только то, что различается
  между средами. Поля, сцепленные с кодом приложения (например containerPort,
  заданный в Dockerfile), остаются в шаблоне — параметр там создал бы способ
  разорвать эту связь.
