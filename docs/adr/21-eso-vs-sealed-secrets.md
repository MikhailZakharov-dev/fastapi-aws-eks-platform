# ADR: доставка секретов — External Secrets Operator, а не SealedSecrets

- **Статус:** принято
- **Контекст:** приложению нужен пароль от базы в переменной окружения. До этого
  Secret создавался вручную: не воспроизводился при пересоздании стенда, отсутствовал
  в git и потому не был частью желаемого состояния кластера. Варианты:
  - **ESO + Secrets Manager**: в git лежит ссылка на внешний секрет, оператор в кластере
    тянет значение и создаёт обычный k8s Secret;
  - **SealedSecrets**: значение шифруется публичным ключом контроллера, **шифротекст
    коммитится в git**, контроллер расшифровывает его приватным ключом.
- **Решение:** ESO + Secrets Manager.

## Почему в этом контексте

**Источник истины уже снаружи и не наш.** Пароль генерит и хранит сам RDS
(`manage_master_user_password`), и при каждом пересоздании базы он новый. SealedSecrets
завёл бы в git **вторую копию** этой истины, расходящуюся с оригиналом при каждом
пересоздании: пришлось бы вручную доставать новый пароль, шифровать и коммитить.
ESO не копирует значение, а ссылается на него.

**Ротация сводится к одной операции.** Поменял значение в Secrets Manager — оператор
подтянет его по `refreshInterval`. У SealedSecrets ротация это цепочка: достать, зашифровать,
закоммитить, пройти ревью, дождаться синхронизации.

**Шифротекст в git — отложенный риск на всю историю.** Попав в коммит, он остаётся там
навсегда, включая уже ротированные пароли. Компрометация приватного ключа контроллера
расшифровывает не текущее значение, а всю историю разом. У ESO в git нет значений вообще.

## Когда SealedSecrets был бы лучше

Когда внешнего хранилища нет: on-prem без облачного секрет-менеджера, отсутствие бюджета
на управляемый сервис, требование держать всё в одном репозитории. Тогда шифротекст в git —
разумный компромисс, а не недостаток. Здесь Secrets Manager уже существует и уже является
источником, поэтому выбор определяется контекстом, а не превосходством инструмента.

## Цена выбранного решения

- **ARN секрета нестабилен.** Managed-пароль RDS живёт в секрете с генерируемым именем,
  и при каждом пересоздании базы ARN меняется — значит `database.secretArn` в values нужно
  обновлять после каждого поднятия стенда. В проде база не пересоздаётся, и это разовая
  настройка; на пересоздаваемом стенде это регулярное трение, принятое осознанно.
- **Secret по-прежнему лежит в etcd**, и по-прежнему в base64. ESO не устраняет секрет
  из кластера — он устраняет секрет из git и переносит управление им во внешний источник.
- **Появляется runtime-зависимость**: если оператор не работает или роль потеряла права,
  Secret не обновится. Раньше отказ был невозможен, потому что Secret был статичен.

## Права

Роль ESO ограничена `GetSecretValue` и `DescribeSecret` на **ARN одного секрета**, а не на
весь Secrets Manager. Доверие роли задано условием на claim `sub` вида
`system:serviceaccount:<namespace>:<имя SA>` — то есть роль может принять ровно один
ServiceAccount, а не любой под кластера. Плюс условие на `aud`, чтобы годился только
токен, выпущенный для STS.
