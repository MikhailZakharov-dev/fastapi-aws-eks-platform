# ADR: prod синхронизируется автоматически, единственный вход — merge request

- **Статус:** принято
- **Контекст:** у prod-окружения появляется собственная Application. Надо решить, что
  считается разрешением на изменение прода. Два варианта:
  - **автосинк** — Application с `automated.selfHeal`, как у dev; изменить прод можно
    только влив MR в gitops;
  - **ручная синхронизация** — `automated` не задаётся; MR влит, git обновлён, но кластер
    ждёт, пока человек нажмёт sync.
- **Решение:** автосинк. Мерж и есть релиз.

## Почему

**Дрейф становится невозможным по построению.** При автосинке состояние «git и кластер
разошлись» всегда означает неполадку, и его можно алертить. При ручном синке это же
состояние — штатное: между мержем и нажатием sync прод легально отличается от git. Отличить
«ещё не выкатили» от «кто-то поменял руками» без человека уже нельзя, и главный смысл
GitOps — сравнимость желаемого с фактическим — теряется ровно в том окружении, где он
нужнее всего.

**Пауза между решением и выкаткой ничего не добавляет.** Аргумент за ручной синк — выбирать
окно выкатки. Здесь окно не нужно: нагрузки, которую надо щадить, нет, а сама выкатка уже
проходит без ошибок (см. постмортем 26). Пауза дала бы только лишнее состояние для
отслеживания.

**Точка контроля одна и уже существует.** Ревью MR — это то место, где решение принимается
и записывается. Добавлять вторую точку (нажатие sync) значит размазать ответственность:
аппрув перестаёт быть достаточным условием, но и нажатие само по себе ничего не проверяет.

## Цена решения

- **Отменить релиз можно только другим мержем.** `selfHeal` возвращает кластер к git,
  поэтому ручное вмешательство живёт до ближайшей сверки. Канонический откат — `git revert`
  bump-коммита; `argocd app rollback` создаёт состояние, которого нет в git, и автосинк
  будет с ним бороться. Это осознанное следствие, а не побочный эффект.
- **Момент выкатки определяется моментом мержа.** Смержил в конце дня — поедет в конце дня.
- **`prune: true` доводит принцип до конца:** удалённый из чарта ресурс исчезает и из
  кластера. Значит ошибочный MR может не только изменить прод, но и удалить из него объект.

## Известный пробел

**Требование «только через MR» здесь процедурное, а не техническое.** Ветка `main` в
gitops-репозитории не защищена, потому что в неё напрямую пишет джоба `deploy-dev`, бампая
тег dev. Значит ничто не мешает отредактировать `values-prod.yaml` мимо MR — дисциплина
держится на договорённости.

Закрыть это можно двумя способами, оба за пределами текущего объёма: перевести и dev-бамп
на MR с автомержем, после чего защитить `main`; либо развести окружения по разным ветвям
или репозиториям, чтобы защита `main` не конфликтовала с автоматикой dev.
