# Секрет в истории git: удалить файл недостаточно

- **Symptom:** файл с учётными данными закоммичен и запушен. Следующим коммитом
  файл удалён — в рабочем дереве его больше нет, но сканер по-прежнему падает.

- **Signal:** джоба `secrets` (gitleaks) на двух последовательных прогонах.
  Оба раза находка указывает на **один и тот же коммит** — тот, где файл появился,
  хотя второй прогон выполнялся уже на коммите без файла:

  ```
  Finding:     DB_PASSWORD=REDACTED
  File:        .env.production
  Commit:      1ddc3aa3d109be9f69d8d1a7b20a5b1b73952543
  Link:        https://gitlab.com/.../blob/1ddc3aa3.../.env.production#L1
  27 commits scanned. leaks found: 1
  ```

  Ссылка из вывода рабочая: значение открывается в веб-интерфейсе по хэшу коммита,
  несмотря на отсутствие файла в HEAD.

- **Cause:** коммит неизменяем, а удаление файла создаёт новый снимок, не трогая
  предыдущие. Значение остаётся объектом в репозитории и доступно по хэшу. Плюс к
  этому оно уже разошлось: клоны, форки, кэши CI, бэкапы хостинга, локальные копии
  других разработчиков.

- **Fix (порядок важен):**
  1. **Ротация значения в источнике** — обязательный и первый шаг. Только он делает
     утёкшее бесполезным. Чистка истории может не сработать вовсе, а ротация работает
     независимо от того, сколько копий разошлось.
  2. **Переписывание истории** (`git filter-repo` или BFG + force-push) — второй шаг,
     дорогой: ломает существующие клоны и требует согласования. Имеет смысл при
     приватном репозитории с известным кругом копий.
  3. **Отпечаток находки в `.gitleaksignore`** — если историю переписывать не будут,
     но инцидент отработан: иначе один старый коммит блокирует пайплайн навсегда.

- **Prevention:**
  - Сканирование истории в CI (`gitleaks git`), а не только рабочего дерева.
    Обязательно с `GIT_DEPTH: 0`: при мелком клоне по умолчанию находка в старом
    коммите не обнаружится.
  - `--redact` в команде сканера: иначе найденное значение печатается в лог
    пайплайна, и инструмент против утечек сам её и совершает.
  - Секреты не должны попадать в репозиторий в принципе. `.gitignore` от этого не
    защищает — в этом разборе файл добавлен через `git add -f` одним флагом.
    Работает только доставка из внешнего источника (см. ADR 21) плюс сканер как сетка.

- **Отдельно про класс отказа:** джоба сканера в первом варианте упала с
  `unknown command "sh" for "gitleaks"` — образ имеет `ENTRYPOINT` с самим бинарём,
  а раннер запускает `script` через шелл. Лечится `entrypoint: [""]`. Ошибка приходит
  от слоя запуска, а не от инструмента: инструмент не стартовал вообще.
